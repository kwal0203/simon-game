## Technical Design Document

## Context and overview

A web-based version of the Simon Game is being built and publicly deployed. The game is being implemented as an MVP that needs to support at least five concurrent players along with a score leaderboard.

This document outlines the technical aspects of the project including system architecture, request flows through the system, data model, API, consistency and correctness semantics, failure modes, infrastructure, observability, security and rollout plan.

## Goals, constraints and non-goals

Technical goals:

* GET leaderboard p95/p99 of 200ms/500ms
* POST leaderboard p95 300ms
* Static game assets cached close to user (CDN)
* Protect database from high request load
  * Redis cached leaderboard
  * Leader-follower pattern where writes only to primary database, reads on read replicas

Constraints:

* Less than $10 per month deployment costs
* Two week implementation
* Support at least 1000 concurrent players without degrading the read or write path
* Python, FastAPI backend
* React frontend
* Leaderboard allowed to be maximum of 10 seconds stale

Non-goals:

* Authentication \+ login/logout UI
* Asynchronous workers and job queues on the backend

## System architecture

![][image1]

The two main paths through the system are labeled A (get leaderboard path) and B (write leaderboard path).

Path A: When the user wants to see the top 100 scores in the game, the /v1/leaderboard endpoint is called. The API service checks the Redis cache to see if a fresh leaderboard is available and returns it if it is. If the player has submitted a score previously, their rank (stored locally in path B) will be added to the leaderboard. If a fresh leaderboard is not in the cache, the API service queries the database, SETs the fresh leaderboard in the cache and returns the current view of the leaderboard (i.e. the top 100 scores).

Path B: When the user finishes a game, their achieved score is written to the system database via a POST request to /v1/scores. This request is idempotent so the header contains an idempotency key generated on the client side and a player\_id in a cookie generated on the server side. The API service INSERT the score into the database, invalidates the leaderboard cache and returns a 201 to the user with the score ID number in the database and the rank at the time the INSERT was performed.

## Data model and schema

### Table

* score\_entries

### Columns

* score\_id (UUID): Generated by backend upon insertion into database
* score (Integer): Length user achieved in the game
* player\_id (UUID): Generated by backend, stored on user side cookie
* Idempotency\_key (UUID): Generated on clientside, used to prevent duplicates on retry
* created\_id (Timestamp): Generated by backend, is the time score was inserted into database
* display\_name (String): User selected display name

### Constraints and indices

* PRIMARY KEY(score\_id)
* INDEX(score DESC, created\_at DESC): Used to allow efficient lookup of top 100 scores in the system
* UNIQUE(idempotency\_key, player\_id): Used to prevent duplicate scores being added to leaderboard on retry

## API design and data contracts

### Retrieve leaderboard

Method: GET /v1/leaderboard
Response: 200 OK
{
  “scores”: \[
    {
      score: Integer,
      rank: Integer,
      display\_name: String
    },
    {
      score: Integer,
      rank: Integer,
      display\_name: String
    },
  \]
}

### Insert score into leaderboard

Method: POST /v1/scores
Headers: idempotency\_key (UUID)
Cookie: player\_id (UUID)
Request body:
{
  “score”: Integer,
  “display\_name”: String
}

Response: 201 Created
{
  “score\_response”: {
    “score\_id”: UUID,
    “rank”: Integer
  }
}

Error responses:

* 400 Bad Request: Missing request body fields (display\_name, score) or idempotency\_key in request header
* 409 Conflict: If same (player\_id, idempotency\_key) submitted, returns most recent score response (scored\_id, rank)

## Consistency and correctness semantics

### Leaderboard

* Top 100: Eventual consistency (\<= 10 seconds stale data allowed)
* Rank: As of the moment the score was inserted into the database
* Inserts into the database are idempotent

## Failure modes and resiliency

### Cache down (read path)

If the cache is down, the system falls back to querying the database read replicas directly

### Cache stampede

Request coalescing is implemented at the API layer to stop a rush of requests to the read replicas upon cache invalidation. The first request to observe the stale cache is redirected to the read replicas while the rest of the requests are held in memory until a fresh leaderboard is written to the cache.

### Database unavailable

Read path: The system will attempt to serve data from the cache. If the cache is not available, return 503 Service Unavailable.

Write path: The API service will return a 503 Service Unavailable. The score will be saved on the client side and the request will be retried until the database service becomes available again.

### Duplicate score submission

Handled by the database UNIQUE(idempotency\_key, player\_id) constraint. Re-tries with the same idempotency key and player id will receive a 409 Conflict response and the duplicate scores will not be written to the database.

### Abuse

Not explicitly handled in V1. Is the post deployment hardening phase rate-limiting on the player\_id will be implemented.

## Deployment and infrastructure

### Hosting

All system components will be deployed onto an AWS EC2 instance
Each service will be packaged into a Docker container

### Domain

Publicly accessible URL (name not confirmed yet)

### Environments

Development, staging and production environments will be used

### CI/CD

Github actions will be used for CI/CD

### Secrets/config management

Secrets will be managed by GitHub Secrets and injected as environment variables into a .env file that is securely copied to the EC2 instance during the CI/CD pipeline

### Networking (domains, TLS)

DNS: A-records will point at EC2 elastic IP
Reverse proxy: NGINX will route requests to the appropriate deployed Docker image (i.e. FastAPI API service or React frontend).
TLS/HTTPS: Free SSL certificates will be provisioned and renewed by Let’s Encrypt

### Migrations strategy and rollback approach

Database migration will be handled by Alembic to ensure PostgreSQL schema changes are version-controlled. Migrations must be backwards compatible.

Code rollbacks will be handled by GitHub Actions which redeploys the previous Docker image tag.

Health check: A /health endpoint will be added to the FastAPI API service that checks for database connectivity.

## Security and abuse controls

Document the identity/auth model (even if anonymous), input validation, rate limiting, CORS/CSRF considerations, and basic abuse mitigation. Note how secrets are protected and any threat assumptions.

### Infrastructure security

Network isolation: The EC2 instance networking will be set up on the basis of the principle of least privilege. Only ports 80 (HTTP) and 443 (HTTPS) will be exposed to the public internet. The database port 5432 (PostgreSQL) will only be reachable from the FastAPI API service Docker container.

Database privileges: Database operations will be limited to INSERT and SELECT operations via a restricted user role. DROP operation on the score\_entries table will not be possible which prevents the damage hackers can do if they get access.

### Application security

Input validation and sanitization: PyDantic will be used to validate inputs. The display\_name parameter will be limited to a maximum of 20 characters and all HTML/JavaScript will be stripped to prevent XSS attacks on the leaderboard.

Cross-origin resource sharing: The FastAPI API service will be configured to only accept cross-origin requests from the React frontend thereby rejecting any requests from third-party websites.

SQL injection: To prevent SQL injection attacks, SQLAlchemy will be used to execute all database operations. SQLAlchemy ORM parameter binding functionality sanitizes inputs automatically which will prevent SQL injection attacks.

### Abuse mitigation

Rate limiting: To prevent automated spamming of the leaderboard, rate-limiting will be applied to the /v1/scores endpoint. An initial limit of 5 requests per IP address every minute will apply.

Score sanity checking: To prevent players submitting very large, fake scores, an upper limit on scores the system will accept will be set to 100\. This is not a humanly reachable score so any score at or above this should be considered to be abuse.

Limitation: This application runs on the client-side so it’s impossible to stop a player manipulating the game memory to submit fake scores. The only way to fully prevent this is to move the gameplay to run on the server but this is out of scope for V1.

## Alternatives considered

### Database

Selected: PostgreSQL
Why NoSQL was rejected: A no SQL database like DynamoDB or MongoDB could have been selected. A core feature of the application is the sorted score list which is handled by the database. PostgreSQL natively supports B-Trees to create an index for this whereas doing this with a NoSQL database would require an external aggregation pipeline which is unnecessary complexity for V1.

### API

Selected: HTTPS
Why Websockets were rejected: Websockets provide a persistent two-way communication pattern between the client and server. This would be useful for multi-player games but V1 of the Simon Grame is single-player and runs on the client side only. The benefit of Websockets to open a connection with the database for leaderboard operations is marginal and would lead to a waste of resources during gameplay. Leaderboard reading and writing only needs to happen at the end of each game.

### Compute

Selected: Docker on EC2
Why AWS serverless was rejected: The benefit of the serverless option would be automatically scaling for 1000s of players. However, this would come at the cost of cold-start time for database reading and writing which could jeopardize the p95 latency constraints of the system. Also, managing database connection pooling between 1000s of ephemeral lambda functions introduces additional complexity above a long-running FastAPI service.

## Rollout plan and milestones

### Context and rollout strategy

The rollout will follow a milestone driven approach progressing through local implementation and testing, to Dockerization of the application, to live MVP deployment on EC2 and production hardening and scaling.

### Milestone 1: Local MVP \+ core logic

Goal: Prove gameplay works on localhost

Execution:

1. Initialize the PostgreSQL database with the score\_entries schema using Alembic migrations
2. Implement FastAPI backend
   1. GET /v1/leaderboard
   2. POST /v1/scores
3. Implement React frontend
   1. Gameplay and leaderboard UI, idempotency\_key in Header and player\_id in Cookie for writes.
4. Run on localhost
   1. Ensure database rejects duplicate score writes

### Milestone 2: Production deployment

Goal: Ship the game to the public internet securely

Execution:

1. Dockerize the React frontend, FastAPI backend and Nginx reverse proxy
2. Provision the EC2 instance and set up security groups so that only ports 80 and 443 are reachable from the public internet (port 5432 blocked)
3. Set up GitHub Actions for CI/CD and GitHub Secrets for injection database credentials securely into the EC2 instance
4. Point the A-names of the domain to the elastic IP address of the EC2 instance. Provision Let’s Encrypt certificates

Validation:

1. Manual testing through browser
   1. Game reachable on public internet
   2. Leaderboard can be retrieved
   3. Leaderboard can be written to idempotently

### Milestone 4: Production hardening and scaling

Goal: Protect the database from cache stampede, abuse and at least 1000 concurrent players

Execution:

1. Provision CDN for static game assets
2. Provision the Redis cache layer
3. Configure read replicas
4. Update GET /v1/leaderboard endpoint to implement the cache-aside pattern
   1. Check Redis
   2. \[hit\] return leaderboard to player
   3. \[miss\] Query read replica
   4. \[miss\] \]Write cache (TTL 10 seconds)
5. Update POST /v1/scores endpoint to implement rate-limiting
   1. Implement IP based rate-limiting of 5 requests per minute for each IP

Validation:

1. Load testing with Locust to ensure p95/p99 latencies for read and write paths.
